## 안정화와 갈피 문학잡지형

커밋 0b053d6(로컬, push 안 함).

자동 확인: tsc 오류 없음, 테스트 203개 통과(타이머 복구 5개 추가).

화면 확인: 에뮬레이터 릴리스 빌드에서 했습니다. 실기기로는 보지 못했습니다.

시험은 모두 별도 시험 설치에서 했습니다. 실제 사용 중인 앱(com.chaekjang.app) 데이터는 건드리지 않았습니다.
- 시험 설치 이름은 com.chaekjang.app.qa였다가, 뒤에서 말할 패키지 이름 변경 뒤로는 app.covebook.qa입니다.

### 먼저 알릴 것: 앱 패키지 이름이 바뀌어 있습니다
- 작업 중 app/app.json의 android.package와 android/app/build.gradle의 applicationId가 `com.chaekjang.app` → `app.covebook`으로 바뀌어 있었습니다(파일 시각 20:33).
- 제가 바꾼 것이 아니고, 이 폴더에서 돌던 다른 작업도 찾지 못했습니다. 의도한 변경일 수 있어 되돌리지 않았고, 커밋에도 넣지 않았습니다.
- 이대로 빌드하면 안드로이드에서는 다른 앱으로 설치됩니다. 기존 com.chaekjang.app의 기록은 자동으로 옮겨지지 않으니, 백업 → 복원으로 옮기거나 이름을 되돌릴지 정해 주세요.

### 1. 첫 실행 지연과 멈춤

#### 단계별 측정
측정 번들에 `[boot]` 표시를 넣었습니다.

같은 릴리스 환경에서 예시 18권 책장(저장하지 않는 측정용)으로, 전·후 APK를 번갈아 3번씩 콜드 스타트했습니다. 앱 시작 기준 ms이고, 가운데 값입니다.

| 단계 | 전 | 후 |
|---|---|---|
| JS 실행 시작 | 800 | 628 |
| 저장소 준비·홈 첫 렌더 | 1362 | 964 |
| 첫 화면 표시(Displayed) | 1759 | 1222 |
| 18권 책 그림 준비 끝 | 4807 | 3332 |
| 조작 가능(JS가 50ms 안에 연속 응답) | 5344 | 3934 |
| 책 그림 계산 시간 합(18권) | 747 | 660 |

- 첫 화면이 보이는 시점과 실제로 조작 가능한 시점 사이가 2~3초입니다. 이 시간에는 책 그림을 한 권씩 만들고, 글꼴 파일(8.4MB)을 Skia가 읽습니다.
- 첫 화면에 필요한 저장소 읽기(서재·배치·설정·시점)는 모두 합쳐 약 120ms였습니다. 외부 요청은 시작할 때 없습니다.
- 빈 책장: 첫 화면 약 1.3초, 조작 가능 약 2.2초(재실행 기준)입니다.
- 설치 직후 첫 실행: 첫 화면 4.2초, 조작 가능 5.5초(전 빌드 1회). 설치 직후 첫 실행은 전·후를 같은 조건으로 비교하지 못했습니다.
- 지난번 20~40초는 이번 측정에서 재현되지 않았습니다.
  - 같은 날 에뮬레이터가 느려진 상태(load 10 이상)에서는 같은 앱이 첫 화면 9~13초, 조작 가능 19~26초까지 늘었습니다.
  - 그래서 환경 영향이 큰 것은 맞지만, 이것만으로 원인을 확정하지는 않았습니다.
  - 실기기 측정은 하지 못했습니다.

#### 실제로 고친 것
- 번들이 12.4MB → 4.5MB로 줄었습니다. 원인은 아이콘 묶음 가져오기였습니다. lucide 아이콘을 묶음째 가져와 아이콘 1,500여 개가 다 들어가 있었고(원본 기준 1.7MB, 하루 사이 번들이 5.7MB에서 12.4MB로 커짐), 쓰는 27개만 하나씩 가져오게 바꿨습니다.
- 쓰지 않던 Skia 굵은 글꼴(8.2MB)을 더 읽지 않습니다. 제목 굵기는 보통 글꼴 + 윤곽으로 만들고 있었습니다.
- 책등 글자를 칸마다 React로 그려 기록하던 방식을 바로 기록하는 방식으로 바꿨습니다.
- 진행 중 독서 복구 읽기를 첫 화면 대기에서 뺐습니다(뒤에서 읽고 복구 창을 띄움).

#### 메뉴 멈춤(ANR)
- 로그: 앱 ANR 두 건(09:44, 09:54)의 스택을 시스템 기록에서 읽었습니다.
  - 메인 스레드는 JS가 아니라 `HardwareRenderer.setStopped`과 `InputEventReceiver.finishInputEvent`에서 기다리고 있었습니다.
  - 그때 앱 CPU는 커널 58%, 메이저 페이지 폴트 1,480회였습니다. 메모리 부족으로 스왑 중이었다는 흔적이고, 앱 코드가 막혀 있던 것은 아닙니다.
  - 두 번째 ANR 때도 JS 스레드는 쉬고 있었습니다.
- 재현 시험: 반투명 옵션을 다시 켜서(측정용 `?menutl=1`) 메뉴 열고 닫기를 10번, 끄고 10번 했습니다. 두 경우 모두 ANR은 0건이었고 창 초점도 정상이었습니다.
- 결론
  - 반투명 옵션이 원인이라는 증거는 찾지 못했습니다(기본값은 계속 끔).
  - 기록된 ANR은 메모리 압박 중에 난 것으로 보입니다. 앱 메모리(PSS 약 290MB)를 줄이는 쪽으로 대응했습니다(굵은 글꼴 제거, 번들 축소).
  - 원인을 확정하지는 못해 '잠정'으로 남깁니다.

### 3. 타이머 복구 기준
앱이 꺼진 정확한 시각은 알 수 없다고 보고 다음처럼 계산합니다.
- 달리는 동안 5초마다, 그리고 백그라운드로 갈 때 '마지막 확인 시각'과 누적 시간을 저장합니다.
- 다시 켰을 때 달리는 상태로 남아 있으면 앱이 꺼진 것으로 봅니다.
  - 센 시간 = 누적 + (마지막 확인 시각 − 이번 구간 시작)
  - 그 뒤(최대 5초 + 꺼져 있던 시간)는 넣지 않습니다.
  - 곧바로 일시정지 상태로 저장하고, 고를 때까지 복구 표시를 남깁니다.
- 경우별 동작(테스트 5개 + 화면):
  - 실행 중 종료: 마지막 확인까지만 셉니다.
  - 일시정지 중 종료: 누적 그대로 돌아오고 복구 창은 없습니다.
  - 복구 후 고르기 전에 또 종료: 시간이 다시 더해지지 않고 복구 창을 다시 띄웁니다.
  - "그때 끝내기": 끝 시각이 마지막 확인 시각입니다.
- 중복 저장 방지
  - 끝내기를 두 번 불러도 초안은 하나입니다.
  - 저장은 타이머 id로 해서, 두 번 눌러도 기록은 하나입니다(화면에서 연속 두 번 눌러 1회로 확인).
  - 초안을 저장하기 전에 앱이 꺼지면 다음 실행에서 "저장하지 않은 독서 기록이 있어요"로 다시 묻습니다(화면 확인).

### 5. 갈피 문학잡지형(3번 시안) (77·78번)
- 구성
  - 겹친 종이 위 아이보리 카드에 먹색 명조, 왼쪽으로 치우친 조판, 넉넉한 여백입니다.
  - 순서: 쪽수 → 문장(가장 크게) → 가는 줄 → 표지·제목·저자·쪽수·날짜 → (메모)
  - 테이프와 찢긴 아래 가장자리는 코드로 그렸습니다. 문장과 정보는 모두 실제 텍스트입니다.
- 상세 화면
  - 같은 책 갈피를 좌우로 넘기고, 개수 표시가 있습니다.
  - 아래 막대: 책장한켠 · 수정 · 공유
  - 더 보기: 수정·연결된 책 열기·삭제
- 긴 문장
  - 글씨는 길이에 따라 27 → 24 → 21 → 19까지만 줄어듭니다.
  - 그보다 길면 카드가 길어지고 스크롤됩니다(긴 문장 전체를 확인).
  - 여러 문단은 문단 사이를 띄웁니다.
  - 긴 책 제목은 세 줄로 다 보입니다.
- 한국어 줄바꿈
  - 안드로이드는 한글을 글자마다 끊어 "투쟁한/다"처럼 낱말 가운데서 줄이 바뀌었습니다.
  - 낱말 연결 문자(U+2060)는 먹히지 않아서, 낱말 단위로 감싸는 방식으로 바꿨습니다.
  - 이제 띄어쓰기에서만 줄이 바뀝니다(짧은·긴·여러 문단·긴 제목 모두 확인).
- 목록: 같은 문법으로 문장 여섯 줄까지 보여 줍니다. 오늘의 갈피는 위에 작게, 책 필터 칩은 한 줄로 줄입니다.
- 공유 이미지는 화면 카드를 그대로 이미지로 뜨고, 개인 메모는 기본으로 뺍니다.
- 4번 풍경형은 추가하지 않았습니다(추후 공유 테마 후보).
